# 모듈 간 출력 형식 차이 — 맞춰야 할 것

작성 2026-10-05 · 권찬결

`common/LLMTrace_Modular` (수연, 10-02 기준) 와 `claude_app` (찬결, 10-05
기준) 의 산출물을 **실제 파일을 열어** 대조했다. 합쳐서 `main` 에 올리기
전에 정해야 할 것만 적는다.

**어느 쪽이 맞다는 주장이 아니다.** 둘 다 각자 맞는 이유가 있다. 다만
`main` 에 두 표가 섞여 들어가면 열 제목은 같은데 값을 읽는 법이 달라져서,
나중에 합칠 때 조용히 틀린다.

---

## 1. `behaviors.csv` — 열은 맞는다

앞 14열이 **이름도 순서도 1:1로 같다.** 좋은 출발점이다.

```
id, question, behavior_id, behavior_name, confidence,
when_from, when_to, span_sec, actor, rule_id,
when_basis, note, alternatives, supported_by
```

차이는 15번째 하나.

| | 수연 | 찬결 |
|---|---|---|
| 열 수 | 14 | **15** (`source_artifacts` 추가) |

`source_artifacts` 는 "이 추론이 어느 **아티팩트 종류**에서 나왔나" 를
`supported_by` 와 별도로 적는 열이다. 없으면 추론 한 줄의 출처를 알려고
`observations.jsonl` 을 매번 되짚어야 한다.

**끝에 붙어 있어서 앞 14열만 읽는 도구는 그대로 돈다.** 공통 명세
`도구_공통명세_v1.md` §5 는 15열로 적혀 있다.

→ **정할 것**: 15열로 통일할지, 아니면 14열을 공통으로 두고
`source_artifacts` 를 선택 열로 둘지.

---

## 2. 같은 열, 다른 표기 — 여기가 진짜 문제다

열 제목이 같아서 **합쳐도 터지지 않는다.** 대신 값을 읽는 법이 달라서
조용히 틀린다.

| 열 | 수연 | 찬결 |
|---|---|---|
| `question` | 문장 — `ChatGPT 로그인 행위가 확인되는가?` | 코드 — `Q1` ~ `Q5` |
| `supported_by` | JSON 배열 — `["obs:0001", "obs:0002"]` | 공백 구분 — `obs:0729 obs:0735` |
| `alternatives` | JSON 배열 — `[]` | ` \| ` 구분 평문 |

실제 한 줄씩.

```
수연  inf:0001, ChatGPT 로그인 행위가 확인되는가?, B02, ...,
      [], "[""obs:0001"", ""obs:0002"", ""obs:0003"", ""obs:0004""]"

찬결  inf:0065, Q2, B02, 로그인 (인증), confirmed, ...,
      , obs:0729 obs:0735 obs:0730
```

→ **정할 것** 셋.

1. `question` 은 **코드**인가 **문장**인가. 코드면 코드표가 명세에 있어야
   하고, 문장이면 같은 행위에 같은 문장이 나오도록 고정해야 한다. 지금은
   엑셀에서 `question` 으로 묶으면 두 모듈이 절대 안 묶인다.
2. 다값 필드를 **JSON 배열**로 쓸지 **구분자**로 쓸지. 하나로 정해야 한다.
   JSON 배열은 CSV 안에서 따옴표가 두 겹이 돼 엑셀에서 지저분해지고,
   구분자는 값 안에 구분자가 들어가면 깨진다. 어느 쪽이든 **명세에 박고**
   양쪽이 따르면 된다.
3. 비어 있을 때의 표기 — `[]` 인가 빈 칸인가.

## 3. `problems.csv` — 열이 아예 다르다

| | 열 |
|---|---|
| 수연 (9열) | `id, stage, severity, code, profile, artifact, parser, source_path, message` |
| 찬결 (6열) | `id, source_artifact, source_path, parser, parser_status, parser_note` |
| 공통 명세 §5 | **6열** (찬결 쪽) |

수연 쪽이 더 많은 걸 담는다 — `severity` 와 `code` 는 자동화에서 쓸모가
있고 `stage` 는 어느 단계에서 터졌는지를 알려준다. 명세가 6열인 건 그냥
먼저 쓴 쪽을 적은 것이지 9열이 틀려서가 아니다.

→ **정할 것**: 9열로 넓힐지, 6열을 유지할지. 넓힌다면 명세 §5 를 고치고
양쪽이 같이 바꾼다.

## 4. 10-05 결정 이후에 생긴 것 — 수연 모듈엔 아직 없다

수연 모듈은 **10-02 기준**이라 그 뒤 결정이 안 들어가 있다. 차이가 아니라
**반영 대기**다.

| 항목 | 상태 |
|---|---|
| `report.csv` (통일 4열) | `claude_app` 에 있음 · `LLMTrace_Modular` 에 없음 |
| 아티팩트 등급 (직접/보조) | 〃 |
| `report.html` 구성 | 수연 — Behavior Result / Current Useful Information / Observation Viewer<br>찬결 — 개요 / 행위 토글 / 아티팩트·경로·등급 3열 |
| 통일 CLI 입력 (이미지·환경·저장경로) | 〃 |
| 통일 CLI 출력 구획 | 〃 |

→ **정할 것**: `report.html` 의 3영역 구성과 10-05 의 "개요 + 토글 행위"
구성 중 어느 쪽인지. 수연 쪽 Observation Viewer 는 10-05 결정에 없는
기능이고, 10-05 의 아티팩트 등급 표는 수연 쪽에 없다. **둘을 합치는 게
맞다고 본다** — 개요 + 토글 + 3열 표를 기본으로 하고, Observation Viewer
를 상세 패널로 붙이면 둘 다 산다.

## 5. 거의 같은 것 — 손 안 대도 된다

**`observations.jsonl` 스키마는 사실상 같다.**

공통: `id` `source_artifact` `source_path` `source_locator` `fact_type`
`fact` `parser` `parser_status` `parser_note` `confidence`
`confidence_basis` `actor` `env_profile` `seq` `tz_source` `schema_version`
그리고 `ts_*` 를 최상위로 펼치는 것까지.

수연 쪽에만 있는 것 — `evidence_kind`, `parsed_record`, `timestamps`
(중첩 dict, `ts_*` 와 중복 보유). `schema_version` 은 수연 `0.4` / 찬결 `0.1`.

→ `evidence_kind` 와 `parsed_record` 는 **있으면 쓸모 있고 없어도 안
깨진다.** 선택 필드로 명세에 넣으면 끝. `schema_version` 은 숫자를 맞추자.

`run.json` 은 구조가 다르지만(수연 중첩 / 찬결 평평) **사람이 읽는 실행
기록**이라 자동 대조 대상이 아니다. 급하지 않다.

## 요약 — 정할 것 다섯

1. `behaviors.csv` 15열인가 14열+선택인가
2. `question` 은 코드인가 문장인가
3. 다값 필드는 JSON 배열인가 구분자인가
4. `problems.csv` 는 9열인가 6열인가
5. `report.html` 구성 — 10-05 안과 Observation Viewer 를 어떻게 합칠지

1~4 는 정하는 즉시 양쪽 다 한 줄짜리 수정이다. 지금 정하는 게 싸다.
